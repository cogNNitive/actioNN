## cogNNitive Bootstrap Rule

When the user types **"I want to use https://cognnitive.com/use"** or similar bootstrap/intent phrases:

1. Fetch the manifest at https://raw.githubusercontent.com/cogNNitive/eNNvironment/main/docs/use/manifest.md
2. Parse the `agent-bootstrap:` block for skills to install
3. Run `node scripts/skills-manager.js status` (from a cogNNitive checkout) to compare installed commits against the manifest pinned commits.
4. Install missing skills with explicit consent (`node scripts/skills-manager.js install`).
5. If any skill is outdated: show the diff preview and ask before running `node scripts/skills-manager.js update` — never silent updates, never claim "installed and up to date" without having run the check.
6. For skills with `mcp[]`: download the bundle `url` into `~/.agents/mcp/{name}.bundle.js` and register in opencode.jsonc
7. Present the `workflows[]` menu

Skills provide specialized instructions and workflows for specific tasks.
Use the skill tool to load a skill when a task matches its description.

## User-Level Skill State

`~/.agents/skills-state.json` records what is actually installed on this machine:
per-skill `commit`, `version`, and `updated_at`, written by `scripts/skills-manager.js`
(the lockfile-lite counterpart of lazy.nvim's `lazy-lock.json`).

The manifest at `eNNvironment/docs/use/manifest.md` is the **source of truth** for
desired pins; the state file is only a local record of installed commits and is never
authoritative for what should be installed.

## MCP Bundle â€” On-Demand Download

The `innfo-mcp` server bundle (`.cogNNitive/mcp-bundle.js`) is NOT tracked in git â€” it is downloaded from iNNfo's versioned CDN channel on demand, pinned to the version recorded in `.cogNNitive/mcp-version.json`.

- **First setup**: run `node scripts/update-mcp.js` before using any skill that requires the MCP (e.g. `nn-innfo`).
- **Updates**: the same command checks the manifest for a newer published version and downloads it.
- The skill `nn-skills-lifecycle init` handles this automatically when bootstrapping a workspace.

## Skill Registry â€” Regeneration

To rebuild the registry after adding, removing, or modifying skills:

```bash
node scripts/build-registry.js
```

Options:
- `--root <dir>` â€” Scan additional root (repeatable)
- `--output <dir>` â€” Output directory (default: `.cogNNitive/`)

The script scans every `skills/<name>/SKILL.md`, parses YAML frontmatter (name, description), and writes both the markdown table and the cache JSON. It is safe to run at any time â€” the `.gitignore`d cache file tracks fingerprints, and the markdown file is overwritten on each run.

## Generic Rules (Cross-Project)

Rules that apply regardless of project context. Safe to use in any repository.

### Commit Discipline
- Never add "Co-Authored-By" or AI attribution to commits. Use conventional commits only.
- Do not commit, amend, push, or create PRs unless the user explicitly requests it.

### Interaction
- Default to short answers. Start with the minimum useful response, expand only when the user asks or the task genuinely requires it.
- Ask at most one question at a time. After asking it, STOP and wait.
- Do not present option menus, exhaustive lists, or multiple approaches unless there is a real fork with meaningful tradeoffs.
- If unsure about length or detail, choose the shorter response.
- Never agree with user claims without verification. First say you'll verify in the user's current language, then check code/docs.
- If user is wrong, explain WHY with evidence. If you were wrong, acknowledge with proof.
- Always propose alternatives with tradeoffs when relevant.
- Verify technical claims before stating them. If unsure, investigate first.

### Code Standards
- **NO FALLBACKS**: Never generate fallback code, polyfills, or compatibility shims.
- **NO BACKWARDS COMPATIBILITY**: Never write code that supports outdated APIs, deprecated patterns, or legacy specifications.
- **NO LEGACY**: Strip all legacy cruft on sight. Never include references to previous major versions or migration helpers.
- **CLEAN & CLEAR**: Code must be readable, well-structured, and free of dead paths, unreachable branches, or commented-out blocks.
- **LATEST ONLY**: Every dependency, API call, framework pattern, and specification reference must assume the latest stable version.
- If you encounter code that violates these standards while working on a task, refactor it to comply. Do not ask permission â€” just fix it.

### Skill Loading
- Before every response, self-check: does this request match any skill in `<available_skills>`?
- If yes, read the matching SKILL.md BEFORE generating your reply. Multiple skills can apply at once.

### Skill Version Check (MANDATORY)
- Before loading any managed skill, the agent MUST verify that the installed commit equals the manifest pinned commit by running `node scripts/skills-manager.js status`.
- If the check cannot run (no checkout, no network, script error) or reports `outdated`, `missing`, or `dir-missing`, STOP and ask the user. Never proceed with a possibly-stale skill, and never claim a skill is up to date without the check having run.
- The script lives at `scripts/skills-manager.js` in `cogNNitive/actioNN`; the desired pins live in `eNNvironment/docs/use/manifest.md`.

## cogNNitive-Specific Rules

Rules specific to the cogNNitive ecosystem. These apply to ALL files in this repository.

### Conversation Logging Protocol (MANDATORY)

- Every conversation using NN skills MUST save a transcript or markdown summary to `<workspace_root>/conversations/YYYY-MM-DD_<nombre_modelo>_<titulo_3_a_6_palabras>.md` (or `conversations/YYYY-MM-DD_<titulo_3_a_6_palabras>.md` if no model is active).

### Skill Versioning Convention

All skills in `skills/` MUST include these fields in their YAML frontmatter:

```yaml
---
name: <skill-name>
version: "V_x-y-z"           # Semantic versioning (see defiNNe Â§7)
last_updated: YYYY-MM-DD     # ISO date of last change
metadata:
  source_type: "original" | "mirrored" | "integrated"
  source: "https://github.com/cogNNitive/actioNN"  # For mirrored skills
license: MIT
---
```

`source_type` values:
- **original**: authored here, this repo is source of truth
- **mirrored**: copied from another repo via sync script (`source` field required)
- **integrated**: bundled tool lives in the skill directory

### Semantic Versioning (defiNNe Â§7)

All versions MUST follow Semantic Versioning with hyphen separators: `V_MAJOR-MINOR-PATCH`.

| Increment | When to apply |
|---|---|
| **MAJOR** | Breaking change in structure or semantics |
| **MINOR** | Backward-compatible addition |
| **PATCH** | Bug fix, clarification, examples |

Version format: `V_x-y-z` where:
- `x` = major (breaking changes)
- `y` = minor (feature additions)
- `z` = patch (fixes, documentation)

This is defined in the defiNNe specification at `specs/defiNNe_V_0-1-0_NN.md` (Â§7).

### iNNfo Frontmatter Compliance

All iNNfo documents (models, templates, workflows) MUST follow the iNNfo V_0-1-0 spec:

```yaml
---
spec_version: "V_0-1-0"
spec_url: "<immutable-url>"
level: 3
parent_spec:
  name: "<template>_V_x-y-z"
  url: "<immutable-url>"
model_version: "V_x-y-z"
title: "..."
---
```

Key rules:
- Level 3 models MUST NOT inline template definitions (concepts, markers, matrices).
- Level 3 models MUST rely on `parent_spec` URL + spec resolver for schema.
- The body MUST begin with `> [!NOTE]` admonition.
- Document structure uses `_NN` structural markers (not `_F`, not `_FORMAT`).

### Naming Conventions

- iNNfo documents (V_0-2-0+): `*_NN.md` suffix (e.g., `workflow_V_1-0-0_workflow_NN.md`)
- Legacy FORMAT docs (V_0-1-0): `*_FORMAT.md` suffix
- Transitional (V_0-1-1): `*_F.md` suffix
- Templates directory: `_templates/` (lowercase, underscore prefix) under the workspace root
- Workflow files: `*_workflow_NN.md`
- Source normalization: `*_source_NN.md`
